**5-A. 필요한 경계 검증 확인과 보완**

기존 테스트와 실제 코드를 먼저 대조하여 ‘이미 검증됨 / 누락 / 실패’를 기록한다. 누락되었거나 실제 위험을 해결하는 테스트만 추가하고, 발견된 원인을 수정한다. 목표 테스트 개수나 형식적인 커버리지 비율은 설정하지 않는다.

1. 공개 데이터가 미공개 결과에 의존하지 않는지 확인한다.

- 공개 primary 입력과 공개 시험 정의를 고정한 별도 유효 fixture들을 만든다. 미공개 후속 판정, 수치, 행 순서, 일부·전체 결과 행의 존재 여부, 결과를 서술한 비공개 텍스트를 변화시킨다.
- 공개 후보 선정, 관측, 근거 내용, ID와 공개 파일 해시는 동일해야 한다. 개발자용 통계·출처·warning은 달라질 수 있다. 공개 시험 방법 자체를 바꾼 경우까지 동일하라고 요구하지 않는다.
- 변형 입력도 올바른 출처 형식과 캐시 메타데이터를 가진 별도 자료로 만든다. 해시 검증을 끄거나 잘못된 원본을 정상으로 취급해서 테스트를 통과시키지 않는다.
- 후속 관측이 0건인 경우는 명시적인 개발자용 진단으로 다루되, 이를 음성으로 채우거나 공개 후보를 바꾸지 않는다. 데이터 연결 완료 여부와 공개 패키지 구성 가능 여부를 구분한다.

2. 측정의 의미와 정체성을 보존하는지 확인한다.

- 같은 후보×시험의 여러 행, 다른 조건·반복, 서로 충돌하는 판정을 조용히 덮어쓰거나 평균으로 합치지 않는다.
- 중복 후보 키와 동일 내용의 여러 원본 행을 구분한다. 원본에 반복 여부를 판단할 근거가 없으면 불명확함을 기록한다.
- not_reported 식별자는 원본에서 정보가 없다는 뜻이며 서로 다른 실제 실험 조건이 확인되었다는 뜻이 아니다.
- 단위·endpoint 불일치, 실제 수치 0, 결측, 수치만 있는 기록의 기존 검증을 유지한다.
- 작은 counter fixture에서 active의 의미와 성공 조건이 설정대로 보존되는지 확인한다. 성공 판정 엔진이나 행동 승인 로직을 구현하지 않는다.

3. 시점·파일·실패 경계를 확인한다.

- build로 만들어진 초기 Observation도 released_at ≤ 초기 as_of 조건을 만족한다. 미공개 NormalizedMeasurement에 실행 공개 시각을 미리 넣지 않는다.
- public/만 있는 환경에서 Adapter와 실제 RDKit Auditor가 동작한다. 참조 누락, 해시 불일치, 경로 이탈 거절을 유지한다.
- 원본 오류가 초기에 발견된 경우뿐 아니라 파일 작성을 시작한 뒤 실패한 경우도 검사한다. 불완전 bundle을 정상 완료로 남기거나 기존 정상 산출물을 손상시키지 않는다.
- 현재 수집기의 429, timeout, 일시적 5xx, 빈·HTML·불완전 응답 경로를 확인한다. 유한 retry와 지원하는 Retry-After 처리, 오류 전파, 정상 캐시 보호를 검증한다. 기본 테스트에서는 실제 네트워크를 사용하지 않는다.

**5-B. 개발자용 후속 데이터 감사 보완**

기존 DataAuditReport를 확장하거나 보조 보고서를 조합하여 다음을 집계한다. domain 타입을 보고서 통계 때문에 확대하지 않는다.

- assay별 원본·정규화·포함·제외·오류 행 수와 각 verdict 분포.
- 고유 SID·CID 수, 같은 CID의 여러 SID, SID/CID 충돌, 구조 누락·파싱 실패.
- 후보×시험별 관측 개수, 명백한 중복, 상충 판정, 조건·반복 구분의 한계.
- primary 후보 전체, primary-active 고유 후보, 최종 선택 후보 각각의 수.
- 최종 선택 후보와 실제로 연결되는 후속 관측·고유 후보·후보×시험 조합 수와 판정 분포.
- 관측된 후속 결과가 없는 후보 수. 미측정과 inactive, inconclusive를 따로 집계한다.

모든 집계에 분모와 집계 단위를 명시한다. 후속 전체 분포와 선택 후보에 연결된 후속 분포를 구분한다. 관측 여부에 따른 선택 편향과 조건 불일치를 기록한다. 이러한 정답·coverage 통계는 curator 또는 개발자용 보고서에만 두고 PublicCampaign·공개 근거·런타임 inspect에 노출하지 않는다.

**6-A. 작은 예제를 유지하며 실제 후보군 확장**

기존 5개 후보 설정은 빠른 smoke 예제로 유지한다. 별도의 확장 설정을 추가하여 여러 후속 관측을 사용할 수 있는 실제 자료를 준비한다.

- 기본 확장 정책은 고정 snapshot의 primary-active 고유 SID 전체다. 원본의 실제 규모를 먼저 확인한다. 자원상 상한이 필요하면 공개 primary 정보와 고정 seed만으로 상한을 선언하고 이유를 기록한다.
- 후보 선정 규칙을 확정한 뒤 후속 coverage를 감사한다. 후속 판정·측정 여부·양성 비율을 보고 후보를 선별하거나 seed를 재탐색하지 않는다. 후속 기록이 있는 295개만 조용히 초기 후보군으로 바꾸지 않는다.
- 고유 SID와 CID 대응을 유지한다. 같은 CID인 여러 SID를 합치지 않으며, 구조 요청에서는 중복 CID 요청만 줄일 수 있다.
- 이전 설정이 구조 요청 CID 다섯 개를 고정하고 있다면, 공개 primary 정보에서 선정된 CID를 따라 구조 요청을 구성하도록 필요한 부분을 보완한다. 후보 선정 함수를 fetch와 build에서 일관되게 재사용하고 별도의 상이한 규칙을 만들지 않는다.
- fetch는 필요한 원본·구조를 모으고, build는 준비된 캐시만 읽는 경계를 유지한다. 요청 속도 제한·캐시·batch 처리를 기존 구현에 맞춰 사용한다.
- 새 후보에 대해서도 입체정보 보존과 실제 RDKit 감사를 수행한다. 구조 실패를 몰래 제외하지 않고 기존 명시적 오류·제외 정책을 따른다.
- 확장 결과는 앞 작업의 snapshot 보관 방식으로 새 revision에 저장한다. 초기 as_of, 공개 범위, 비용 가정, 판정 의미를 임의로 바꾸지 않는다.

확장 bundle에 대해 선택 후보 수, 연결된 후속 후보×시험 수, 판정 분포, 미측정 범위, 구조 감사 결과를 보고한다. 후속 관측이 충분하지 않거나 한 종류의 판정만 있다면 그대로 기록한다. 실제 존재하지 않는 시험·정답을 추가하여 자료를 풍부하게 만들지 않는다.

이번 자료 준비의 성공과 학습·평가 적합성은 구분한다. 후속 행이 1건보다 늘었다고 모델 성능 비교나 여러 종류의 시험 선택에 충분하다고 자동 판정하지 않는다. 어떤 반복 실행을 지원할 수 있고 어떤 평가에는 자료가 부족한지 개발자용 문서에 적는다.

**6-B. 2단계 인계 문서 작성**

docs/stage2_data_handoff.md에 현재 실제 타입·파일·함수 이름을 사용하여 다음을 설명한다. 새로운 실행 엔진은 만들지 않는다.

| 연결점 | 인계할 내용 |
|---|---|
| 초기 입력 | DataSource와 PublicBundleAdapter 사용 예, 실제 공개 패키지 위치 |
| 후속 자료 | NormalizedMeasurement 저장 형식·버전 관리, 필드 의미, 원본 출처와 로딩 방법 |
| 조회 단위 | 후보×시험과 condition/replicate 관계, 여러 행이 있을 때 구별 가능한 범위 |
| 결과 근거 | 공개 시 EvidenceRef로 연결할 수 있는 근거 payload·원본 식별 정보 |
| 시점 | 초기 as_of, 원본 실험 날짜, 이후 released_at의 구별 |
| 부재·오류 | 기록 없음, 실제 inactive, inconclusive, 파일·파싱 오류의 구분 |
| 데이터 한계 | 관측 범위·선택 편향·미지정 조건과 평가 시 주의할 점 |

다음 책임은 2단계에 남겨라.

- 승인 및 예산 처리 후 선택된 후속 자료를 Observation으로 변환하고 공개하기.
- 현재 실행 시점을 기준으로 released_at을 부여하고 검사하기. 초기 as_of를 실행 시각으로 덮어쓰지 않기.
- 공개되는 근거를 등록하고 참조 검증에 반영하기.
- 한 행동에 여러 측정이 연결된 경우의 실행 의미, 기록이 없는 행동의 처리와 과금 정책 확정하기.
- 파일·도구 접근 격리, 접수·실행 이력, 중복 실행 방지와 RunState 갱신.

현재 데이터가 이러한 책임을 수행하기에 필요한 원본 식별자나 근거를 빠뜨렸다면 data 산출물을 최소한으로 보완한다. 미측정 결과를 음성으로 만들거나 미리 released_at을 넣는 방식으로 해결하지 않는다. 계약이 불확실한 부분은 명확한 인계 결정 사항으로 적고 임의의 실행 동작을 구현하지 않는다.
